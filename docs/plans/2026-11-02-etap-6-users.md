# Этап 6: пользователи и доступ — план

> **Исполнителям:** задачи по порядку, по одной; проверка — одна итоговая.
> Каждая задача сама доводит тесты и `go vet` до чистого.

**Цель:** несколько пользователей панели с ролями «администратор» и
«пользователь», владельцы клиентов, 2FA (TOTP) с резервными кодами,
список активных сессий с отзывом, белый список IP с таймером возврата,
`azpanel user reset`, проверка прав на каждом маршруте.

**Архитектура:** пользователи и сессии — в SQLite (`internal/store`,
миграция 2). Сессии переживают перезапуск панели. Единственный
администратор из `secrets.env` (`PANEL_ADMIN_USER`/`PANEL_ADMIN_HASH`,
план 2а-2) при первом старте переносится в базу. Права проверяются одним
промежуточным обработчиком по таблице маршрутов.

**Стек:** Go 1.24, стандартная библиотека (TOTP — свой, RFC 6238);
`bcrypt`, `go-qrcode` — уже в проекте.

**Спецификация:** `docs/specs/2026-11-01-azpanel-design.md`,
«Пользователи и доступ», «Настройки» (опасные настройки с таймером).

## Общие ограничения

- Код — латиница; интерфейс, ошибки, журнал — по-русски.
- `go.mod`: `go 1.24` не меняется.
- Пароль: не короче 10 символов, есть буквы и цифры, не равен логину;
  bcrypt cost 12. Логин: `^[a-z0-9_.-]{3,32}$`.
- ID сессии в cookie — 32 случайных байта hex; в базе хранится только
  SHA-256 от него. CSRF — как сейчас, на сессию.
- Секрет TOTP хранится зашифрованным AES-256-GCM ключом `PANEL_DATA_KEY`
  из `secrets.env` (32 байта hex; нет — панель создаёт при старте через
  `secrets.SetMany`). Резервные коды — 10 штук по 10 символов
  (`[a-z2-9]`), хранятся bcrypt-хешем, одноразовые, показываются один раз.
- TOTP: SHA-1, 6 цифр, шаг 30 с, окно ±1 шаг; код, уже принятый в этом
  шаге, повторно не принимается (защита от повтора).
- Ограничение попыток входа (5 за 15 минут на IP) распространяется и на
  второй шаг (код 2FA / резервный код).
- Последнего администратора удалить, понизить или отключить нельзя.
- Смена пароля завершает все остальные сессии пользователя; сброс через
  `azpanel user reset` — все сессии.
- Пользователь с ролью «пользователь» видит только клиентов, где он
  владелец: список, карточку (без форм управления), профили и QR, трафик,
  срок. Чужой клиент — 404 (не 403: не выдавать существование). Маршруты
  администратора — 403.
- Все изменения пользователей и сессий — в журнал действий (`Store.Audit`).
- Коммиты — от syava842@gmail.com, **без `Co-Authored-By` и подписей
  Claude**, по-русски.

### Задача 1: хранилище пользователей и сессий

**Файлы:** `internal/store/users.go`, `sessions.go`, миграция 2 в
`migrate.go`, тесты.

Миграция 2:

```sql
CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  login TEXT NOT NULL UNIQUE,
  hash TEXT NOT NULL,
  role TEXT NOT NULL CHECK (role IN ('admin','user')),
  disabled INTEGER NOT NULL DEFAULT 0,
  must_change INTEGER NOT NULL DEFAULT 0,
  totp_secret BLOB,            -- зашифрованный, NULL — 2FA выключена
  totp_last_step INTEGER NOT NULL DEFAULT 0,
  created INTEGER NOT NULL);
CREATE TABLE backup_codes (user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  hash TEXT NOT NULL, used INTEGER NOT NULL DEFAULT 0);
CREATE TABLE sessions (
  id_hash TEXT PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  csrf TEXT NOT NULL, ip TEXT NOT NULL, agent TEXT NOT NULL,
  created INTEGER NOT NULL, seen INTEGER NOT NULL, expires INTEGER NOT NULL,
  mfa_pending INTEGER NOT NULL DEFAULT 0);  -- 1 — пароль верен, ждём код 2FA
ALTER TABLE client_cards ADD COLUMN owner_id INTEGER REFERENCES users(id) ON DELETE SET NULL;
```

Методы (с `ctx`): `CreateUser`, `UserByLogin`, `UserByID`, `Users`,
`UpdateUser` (роль, disabled, must_change, hash, totp_secret,
totp_last_step), `DeleteUser`, `AdminCount` (не отключённых
администраторов); `SetBackupCodes(userID, hashes)` (заменяет все),
`UseBackupCode(userID, code string) (bool, error)` (сверяет bcrypt,
помечает использованный атомарно); `CreateSession`, `SessionByIDHash`,
`TouchSession` (seen, не чаще раза в минуту), `DeleteSession`,
`DeleteUserSessions(userID, exceptIDHash)`, `UserSessions(userID)`,
`PurgeExpiredSessions(now)`; `SetOwner(node, client, userID *int64)`,
`ClientsOf(userID) ([]ClientRef, error)`.

Тесты: уникальность логина; `AdminCount`; каскадное удаление сессий и
кодов; резервный код срабатывает один раз (два параллельных вызова — ровно
один true); `DeleteUserSessions` с исключением; владелец снимается при
удалении пользователя.

Коммит: «Хранилище: пользователи, резервные коды, сессии, владельцы клиентов».

### Задача 2: TOTP и шифрование

**Файлы:** `internal/panel/totp.go`, `crypt.go`, тесты.

- `NewTOTPSecret() ([]byte, error)` — 20 байт; `TOTPURL(issuer, login string, secret []byte) string` —
  `otpauth://totp/<issuer>:<login>?secret=<base32 без =>&issuer=<issuer>&digits=6&period=30`.
- `TOTPCode(secret []byte, step int64) string`;
  `CheckTOTP(secret []byte, code string, now time.Time, lastStep int64) (step int64, ok bool)` —
  окно ±1, шаг не больше `lastStep` — отказ.
- `Seal(key, plain []byte) ([]byte, error)`, `Open(key, sealed []byte) ([]byte, error)` — AES-256-GCM, nonce впереди.
- Тесты: векторы RFC 6238 (SHA-1, секрет `12345678901234567890`, времена
  59, 1111111109, 1111111111, 1234567890, 2000000000 → 287082, 081804,
  050471, 005924, 279037 для 6 цифр); повтор того же шага — отказ; окно ±1;
  `Seal`/`Open` туда-обратно, подмена байта — ошибка.

Коммит: «Панель: TOTP по RFC 6238 и шифрование секретов».

### Задача 3: вход, 2FA и сессии в базе

**Файлы:** `internal/panel/auth.go`, `server.go`, `login.html`, новый
`mfa.html`, тесты; `run.go` (перенос администратора, ключ данных).

- `Sessions` в памяти заменяется хранилищем: `Server.Store` уже есть
  (план 2а-3). Cookie — ID, в базе — SHA-256.
- Вход: логин+пароль (`CheckPassword` по хешу из `users`; несуществующий
  логин — фиктивный bcrypt, как сейчас). Отключённый пользователь —
  «неверное имя или пароль». У пользователя есть 2FA — сессия с
  `mfa_pending=1`, переход на `/login/2fa`; там код TOTP или резервный
  код; успех — `mfa_pending=0`. Сессия с `mfa_pending=1` открывает только
  `/login/2fa` и `/logout`, живёт 5 минут.
- `must_change=1` — после входа все маршруты, кроме `/account/password`
  и `/logout`, перенаправляют на смену пароля.
- Настройка `panel.require_admin_2fa` (bool, по умолчанию false; добавить
  в `config.Panel` с проверкой): администратор без 2FA после входа
  попадает на `/account/2fa` и не может уйти, пока не включит.
- `run.go`: при старте нет ни одного пользователя, а в `secrets.env` есть
  `PANEL_ADMIN_HASH` — создать администратора с этим логином и хешем,
  журнал «перенесён администратор из secrets.env». Нет `PANEL_DATA_KEY` —
  создать. Раз в час — `PurgeExpiredSessions`.
- Тесты: вход без 2FA; вход с 2FA — без кода только `/login/2fa`; верный
  код — доступ; повтор того же кода во второй сессии — отказ; резервный
  код — один раз; 5 неверных кодов — 429; `must_change` перенаправляет;
  `require_admin_2fa` перенаправляет; перезапуск сервера (новый `Server`
  на той же базе) — сессия жива; перенос администратора из секретов.

Коммит: «Панель: пользователи в базе, вход с 2FA, сессии переживают перезапуск».

### Задача 4: страницы аккаунта и пользователей, права

**Файлы:** `internal/panel/account.go`, `users.go`, `access.go`,
шаблоны `account.html`, `users.html`, `user.html`; правки `clients.go`,
`server.go`, layout; тесты.

- `/account`: смена пароля (старый + новый дважды; завершает остальные
  сессии), 2FA (включить: показать QR и секрет, подтвердить кодом, затем
  показать 10 резервных кодов один раз; выключить — паролем и кодом; новые
  резервные коды), активные сессии (IP, браузер, создана, последняя
  активность; «Отозвать» — любую свою, кроме текущей; «Выйти везде»).
- `/users` (только администратор): список (логин, роль, 2FA, отключён,
  клиентов, последний вход); создать (логин, роль, пароль или «сгенерировать
  16 символов» — показать один раз; «сменить при первом входе» по
  умолчанию да); карточка пользователя: роль, отключить/включить, сброс
  пароля (сгенерировать, показать один раз, все сессии завершаются), сброс
  2FA, сессии с отзывом, список его клиентов; удалить (подтверждение
  вписыванием логина). Защита последнего администратора — на каждом из
  этих действий.
- Карточка клиента (администратор): поле «владелец» (выбор пользователя
  или «нет»).
- `access.go`: таблица прав `routes` — маршрут → `admin` | `any`;
  промежуточный обработчик `s.require(role, h)`; для `any`-маршрутов
  клиентов — функция `s.visibleClient(r, name)`: администратор — все,
  пользователь — только свои (`ClientsOf`), иначе 404. Пользователь не
  видит формы управления в карточке и ссылку «Новый клиент», «Журнал»,
  «Пользователи», «Сейчас» (сервер — дело администратора).
- Тест прав: таблицей перебрать **все** маршруты из `Handler()` под
  пользователем-не-администратором: маршруты администратора — 403; чужой
  клиент — 404; свой клиент — карточка 200 без форм, профиль и QR — 200;
  POST на действия своего клиента — 403. Тест падает, если в `Handler()`
  появился маршрут, которого нет в таблице прав.

Коммит: «Панель: аккаунт, пользователи, роли и проверка прав на каждом маршруте».

### Задача 5: белый список IP с таймером возврата и `azpanel user reset`

**Файлы:** `internal/config/config.go` (`panel.allow_ips []string` — IP
или CIDR, пусто — без ограничения; проверка формата), `internal/panel/allowip.go`,
`pending.go`, `settings_access.html`, `cmd/azpanel/usercmd.go`, тесты.

- Промежуточный обработчик белого списка — до входа, на всех маршрутах,
  кроме `/healthz`; адрес — `remoteHost` (за nginx — этап 2б); не в списке
  — 403 без подробностей.
- «Доступ» в настройках (администратор): правка белого списка.
  Применение — опасное: новое значение действует сразу, в `config.toml`
  пишется, а через 2 минуты, если с нового списка не нажали «Подтвердить»
  (POST с CSRF от адреса, который проходит новый список), прежнее
  значение возвращается в файл и в работу. `pending.go` —
  универсальный механизм `Pending{Key, Old, New, Deadline}` для опасных
  настроек (тот же понадобится 2б для адреса, порта, HTTPS); переживает
  перезапуск — хранится в `meta`. Сохранить список, в который не входит
  текущий адрес, — предупреждение и второе подтверждение.
- `azpanel user reset <логин>` (от root, на сервере): новый пароль
  (16 символов, показать), `must_change=1`, 2FA выключена, резервные коды
  удалены, все сессии завершены, журнал от «root (консоль)». `azpanel
  user list`. `azpanel panel passwd` остаётся как `reset` первого
  администратора (обратная совместимость).
- Тесты: CIDR и одиночный IP; пустой список; адрес не в списке — 403;
  таймер: без подтверждения через 2 минуты (подменённое время) — возврат;
  подтверждение — остаётся; перезапуск в середине таймера — возврат всё
  равно происходит; `user reset` для несуществующего логина — ошибка.

Коммит: «Белый список IP с таймером возврата, azpanel user reset».
